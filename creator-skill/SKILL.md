# React PPT 创作 Skill

## 1. 目标与职责

将用户的主题、材料、表达目标或既有演示，转化为结构清晰、视觉合理、可以实际运行的 React PPT。

本 Skill 负责组织完整的创作过程：

理解任务 → 组织内容 → 设计页面 → React 实现 → 评估与修正。

它是创作流程的入口和协调层，不是所有设计规范、工程细节与评估方法的集合。具体方法按需从 `references/` 加载。

适用于教学课件、科研汇报、组会报告、商业汇报等场景。根据场景选择内容组织、视觉表达和交互方式。

## 2. 判断任务入口

开始工作前，先识别用户提供的材料、希望改变的对象，以及当前任务所处的阶段。

### 参考改编

用户提供了作为本次创作依据的既有 PPT，并要求转换、借鉴、修改或重新设计。

既有 PPT 可以是 PPTX、PDF 导出或逐页截图。

论文、文字、数据、风格图片或其他参考材料本身不属于既有 PPT。

### 从零创作

用户没有提供作为创作依据的既有 PPT，需要从对话、主题、目标、文字材料、论文或其他来源开始组织演示。

### 现有项目续作

用户提供或指定了已有的 React PPT 项目、页面或模块，需要继续制作、修改、修复或优化。

先检查当前实现、工程约束和已有成果，再从实际需要的阶段开始。不要为了执行完整流程而重复已经完成的工作，也不要无故重建已有架构。

如果任务同时涉及既有 PPT 与现有 React 项目，应同时检查原稿要求和当前实现，以用户明确提出的目标为准。

## 3. 两条创作 Workflow

### Workflow A：参考改编

**理解原稿 → 明确保留与调整范围 → 组织页面内容 → 设计页面 → React 实现 → 评估与修正**

1. **理解原稿**
   阅读可用的原稿与配套材料，识别其内容结构、页面顺序、核心信息、视觉特征和需要解决的问题。

2. **明确改编范围**
   判断用户希望忠实转换、局部修改、借鉴风格，还是整体重设计。明确哪些内容、页面和视觉元素必须保留，哪些可以调整。

3. **组织页面内容**
   建立原稿与新页面之间的对应关系。根据任务需要决定保留、拆分、合并、重排或新增页面。不得将整体重设计默认为可以随意改变原稿内容。

4. **设计页面**
   在满足内容要求的前提下，优化信息层级、页面构图、视觉表达和必要的交互。借鉴原稿不意味着必须复制其缺陷。

5. **React 实现**
   根据确定的设计和工程约束完成实现，优先复用适用的现有组件和基础设施。

6. **评估与修正**
   检查内容是否完整、原稿约束是否满足、页面是否正确呈现，以及交互和工程行为是否符合预期。

### Workflow B：从零创作

**理解目的与受众 → 组织叙事与大纲 → 确定视觉方向 → 设计页面 → React 实现 → 评估与修正**

1. **理解目的与材料**
   明确演示的用途、受众、核心目标、可用材料、演示时长及其他明确约束。只对会实质影响结果且无法合理推断的信息进行必要确认。

2. **组织叙事与大纲**
   确定演示要回答的核心问题、主要论点、证据和页面顺序。根据场景选择叙事结构，不套用固定的教学、科研或商业模板。

3. **确定视觉方向**
   根据受众、内容特征与演示目的选择适合的视觉语言、信息组织方式和页面表达形式。必要时比较不同方向。

4. **设计页面**
   将大纲转化为具体页面方案，明确每页的核心信息、内容层级、视觉主体及与前后页面的关系。

5. **React 实现**
   将设计转化为可运行的 React 页面，按实际需要加入图表、图片、动画、视频和交互。

6. **评估与修正**
   从内容、视觉、交互、工程实现及实际使用目的等维度检查结果，修复影响质量的问题并复验。

## 4. 执行原则

### 4.1 从当前阶段开始

Workflow 用于确定方向，不是每次必须完整执行的固定清单。

- 修改单页时，聚焦该页面及必要的上下文。
- 调整整体视觉时，检查全局一致性，避免无关的内容重写。
- 修复工程问题时，优先定位问题并控制修改范围。
- 继续已有项目时，复用已有大纲、组件、资源和评估结果。
- 用户明确要求直接实现时，不应机械地要求逐阶段确认。

如果缺少的信息会导致方向性错误，应先询问；否则采用合理假设继续推进，并在必要时说明假设。

### 4.2 内容先于装饰

每一页都应有明确的主要信息或需要解决的问题，并与整份演示的叙事保持一致。

- 根据演示目标选择页面内容和表达形式。
- 优先建立清楚的信息层级和逻辑关系。
- 图表、图片、动画与交互必须承担表达、解释或操作功能。
- 避免无意义的装饰、内容堆砌、重复表达和不必要的交互。
- 不得为了视觉效果而歪曲数据、改变论证含义或编造事实。

### 4.3 设计与实现相互校验

设计示意图与实际运行页面是不同的产物，不得将示意图视为实现已经完成。

根据任务需要决定是否先生成设计预览、是否分批实现，以及是否需要用户确认。ImageGen 设计图、逐页确认和特定中间文件均不是所有任务的强制步骤。

当用户已经明确设计方向且实现路径清晰时，可以直接实现；当方向存在重大不确定性或返工成本较高时，应先展示足以判断方向的方案。

### 4.4 按需加载参考资料

先判断当前阶段和具体问题，再读取相关文件。不要在开始任务时预读整个 `references/` 和 `scripts/` 目录。

读取资料时，优先使用与当前任务直接相关的规范。若参考文档中的旧规则与本入口或用户当前明确要求不一致，应识别冲突并按适用的工程约束处理，不要机械照搬过时的教学专属要求。

## 5. 共性硬约束

以下约束适用于本 Skill 所创建或修改的演示页面。

### 5.1 固定画布

画布尺寸为 **1600 × 900**。

页面按固定画布设计和实现。展示空间变化时，由外层对完整画布等比例缩放，不通过视口变化重新排列页面内容，也不以裁切、横向滚动或内容溢出掩盖布局问题。

### 5.2 React 实现

正式页面及其状态、交互使用 React 实现。

遵守现有工程的技术栈、页面注册方式、入口契约和组件约定，不为了局部任务随意更换架构或引入新的依赖。

### 5.3 字体Typography

标题、正文、标签、提示等独立文字必须使用 Shared `Typography` 包裹，或使用内部已经封装 `Typography` 的组件。

遵循现有 Typography 的适用方式，不随意绕过统一文字体系。其他 Shared 组件根据实际需要选用，不要求所有页面统一使用 `ContentBlock`、`MathFormulaBlock`、Theme 或 SceneDeck。

### 5.4 工程约束与修改边界

- 本项目每个模块的大纲固定为 `modules/<模块目录名>/outlines.json`，从规划到实现持续维护同一文件；不得另换文件名或存放位置。
- 在当前演示模块内解决局部需求，禁止修改公共组件。
- 涉及模块身份、资源地址和资源目录时，遵循对应的仓库契约。
- 仅在需要时引入脚本、模型调用、GPU 计算或额外依赖。
- 不因参考文档尚未完善，就假定可以忽略现有工程的实际约束。

## 6. 评估与完成条件

实现完成不等于任务完成。根据修改范围和演示目的选择评估方法，不将教学评分标准直接套用到所有场景。

### 内容与结构

检查内容是否准确、关键论点和证据是否完整、页面顺序是否合理，以及是否存在无依据的补充、重复表达或重要遗漏。

### 视觉与布局

检查视觉层级、信息密度、留白、对齐、文字可读性、图表表达，以及元素是否发生遮挡、重叠、越界或裁切。

### 交互与运行

涉及交互时，检查状态变化、操作反馈和实际行为是否符合设计。涉及工程改动时，根据适用情况运行构建、检查脚本并查看页面实际渲染结果。

### 评估方式

- 根据改动选择有针对性的检查，不盲目运行所有评估工具。
- 使用适用的自动化脚本、截图和 Rubric。
- 对重大视觉修改，尽可能检查实际页面截图，而不只检查代码。
- 发现问题后，优先修复影响内容正确性、可读性、布局和核心交互的问题，并进行必要的复验。
- 没有实际执行的测试，不得声称已经通过。

### 完成条件

任务完成时，应满足本次任务的明确目标，并尽可能确认：

1. 页面能够按预期运行。
2. 核心内容和约束得到满足。
3. 不存在已发现且尚未处理的重大布局或交互问题。
4. 适用的工程检查已经执行，或明确说明尚未验证的部分。

最终说明实际完成的工作、关键修改和验证情况，以及仍然存在的限制。根据任务规模控制汇报长度，不输出与任务无关的过程描述。

## 8. 未统一事项的处理原则

以下事项不设为所有场景的统一硬约束，按任务目标、用户要求和现有工程契约决定。

- **设计预览与确认**：根据方向不确定性和返工成本决定，不强制 ImageGen 或逐页确认。
- **讲稿与 Guide**：仅在用户需要或任务目标适用时生成，不视为 PPT 的默认附属产物。
- **视觉系统**：Typography 是统一底线；主题、字体样式、标题区和控件根据整体设计方向确定。
- **播放与工程组织**：优先沿用当前项目架构；不因单次创作强制引入 SceneDeck 或新的注册机制。
- **模块身份与资源**：接入现有模块时遵守仓库契约；不将特定模块的 UUID 或资源规则无条件扩展到所有场景。
- **评估门槛**：采用通用检查项与适用的场景专属 Rubric；不把教学评分门槛当作所有 PPT 的统一验收标准。
- **Shared 修改**：优先局部实现；只有在公共组件确实需要改进时，才评估公共修改的必要性与影响。
