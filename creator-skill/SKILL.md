# 多形态教学内容创作

根据用户提供的主题、材料、需求或参考案例，创作类似 `modules/Neuron-Guide/` 的多形态教学内容模块，帮助学习者更容易理解知识，降低认知负担并缩短学习时间。

所有教学内容都以 **1600×900 的 React 界面**作为基本页面单元。

最终主要以两种形态呈现：

- **Blog / Guide**：由多个 1600×900 页面按照教学顺序纵向拼接，形成适合自主学习和互联网传播的连续阅读体验。
- **PPT**：同样使用 1600×900 页面，但一次只展示一页，用于课堂讲授和演示。

两种形态应共享相同的核心知识、页面顺序和主要交互。区别主要在于浏览方式和使用场景，而不是重新设计两套课程。

## 创作流程

1. **了解质量基线**

   开始新模块前，先阅读 `modules/Neuron-Guide/`，了解本仓库成熟教学模块的内容完整度、工程组织、视觉质量和交互水准。

   `Neuron-Guide` 只作为质量基线和工程参考，不照抄其中的教学思路、页面设计和视觉构图。新的课程应根据自身知识结构重新设计。

2. **对齐用户意图**

   在正式制作前，先理解用户希望讲什么、给谁学习、重点是什么，以及期望的内容风格、视觉效果和交互方式。

   对最终效果存在明显歧义时，先用简短语言描述预计成品的样子，与用户确认关键方向后再实现。

   在制作每一页之前，也可以简要说明这一页预计呈现的内容、主要视觉对象和交互方式，逐步与用户对齐。

3. **建立课程大纲**

   将整体课程大纲保存为模块根目录下的 `outlines.json`，作为 Blog、PPT 和后续实现共同使用的页面索引。

   格式如下：

   ```json
   {
     "title": "课程标题",
     "pages": [
       {
         "id": "01",
         "title": "页面标题",
         "goal": "这一页希望学习者理解或完成什么",
         "summary": "这一页主要讲什么",
         "interaction": "无，或简述需要的交互",
         "next": "这一页如何自然引出下一页",
         "snippet": ""
       }
     ]
   }
   ```

   `outlines.json` 只记录课程结构和页面意图，不承载详细页面设计。

4. **逐页制作**

   根据 `outlines.json` 逐页设计和实现。

   每一页都是独立的 1600×900 React 页面。

   默认先完成一页并检查实际效果，用户确认方向满意后再继续下一页。用户明确要求连续制作时，可以按照已经确认的设计方向继续完成后续页面。


# 设计哲学

**让知识逐渐显现，让操作承担解释，让学习自然发生。**

偏好的课程设计：
- **渐进式披露**：知识逐步出现，一次主要引入一个新变量、关系或任务。
- **无意识学习**：通过熟悉情境、自然操作和巧妙反馈，让学生在不知不觉中形成理解。
- **支架渐隐**：开始给予必要提示和限制，理解后逐步撤去帮助并开放自由度。
- **直接操纵**：优先让学生直接操作知识对象，而不是操作与知识分离的抽象控件。
- **先体验后抽象**：先看现象、操作和规律，再引入概念、术语、公式和代码。
- **认知冲突**：先让学生形成预测，再通过结果推动其修正原有理解。
- **安全失败**：允许尝试、撤销和重做，让错误本身也能提供学习信息。
- **保持连续性**：同一对象在图片、图表、公式和代码之间保持稳定对应。
- **变式与迁移**：改变情境、表征或条件，让学生发现真正不变的知识结构。
- **隐形评价**：尽量通过学习过程和操作行为判断理解程度，减少额外考试对学习过程的打断。
- **自适应教学**：根据学习者当前状态调整解释深度、提示强度和后续路径。
- **界面退后**：优秀交互应像优秀游戏一样自然，让学生关注知识和问题本身，而不是控件和操作说明。


## 自进化策略

在与用户持续协作的过程中，逐步总结其稳定的课程设计偏好，包括表达方式、审美倾向、教学取向、内容取舍、交互偏好和工作方式，并用这些信息提高后续创作与用户预期的匹配度。

尚未得到用户明确确认的偏好，只作为可修正的推测，不视为既定事实，也不推断与课程创作无关的人格或敏感特征。

将长期有效的信息记录在：

`creator-skill/souls/soul.md`

按以下三类维护：

- **用户喜欢**：已经通过明确反馈或多次选择确认的偏好。
- **用户不喜欢**：已经明确否定，或多次要求避免的设计、表达和工作方式。
- **推测用户可能喜欢**：根据当前反馈推测出的潜在偏好，后续根据用户反馈继续验证、修正或删除。这里的内容要给用户一种感觉，就是他自己看见就很喜欢，可能自己都没意识到。

记录应具体、简短、可执行，重点描述这些偏好会如何影响课程内容、视觉设计和交互方式，避免记录宽泛的人格标签。

## 必须遵守的条例

以下规则属于仓库级约束，不因课程风格不同而改变。

1. **优先复用 Shared UI。** 开发新页面或组件前，先检查 `modules/shared/react/`。已有对应能力时必须直接复用，不重复实现按钮、输入框、滑杆、提示、问题、公式、渐进展示、课程流程、图表等通用组件。只有知识本身需要的特殊视觉或交互才在模块内新增组件。不得复制 Shared 组件另起一套近似实现，也不要为了单个页面修改 Shared 的公共行为。

2. **所有独立文字使用 `Typography`。** 页面标题、副标题、正文、说明、标签、提示等文字统一通过 Shared `Typography` 渲染，或使用内部已经封装 `Typography` 的 Shared 组件。模块 CSS 不得自行覆盖 Typography 的 `font-size`、`font-weight` 和 `line-height`。

3. **遵循 Shared Theme。** 颜色、字体、圆角、边框、阴影和状态色优先使用 `modules/shared/react/` 已定义的 CSS Token，不在模块内重新建立基础视觉规范。模块 CSS 主要负责页面布局和课程专属视觉。

4. **所有教学页面固定为 1600×900。** Blog / Guide 和 PPT 都以 1600×900 React 页面为基本单元，不改变逻辑画布尺寸。

5. **所有内容必须完整容纳在画布内。** Grid 和 Flex 子项必须可收缩，优先使用比例布局和 `minmax(0, 1fr)`。图片、SVG、Canvas、公式、图表和交互组件应限制在父容器内，不得依靠裁切、固定宽度堆叠或横向滚动解决溢出。完成页面后必须实际检查最终渲染效果。

6. **一页只有一个主要视觉重点。** 页面应具有明确阅读顺序，优先使用少量大区域表达知识关系，避免多层嵌套卡片和 Dashboard 式布局。

7. **严格遵守模块边界。** 课程专属图片、数据、组件和模型代码存放在当前模块目录中，真正跨课程复用的能力才进入 `modules/shared/`。活跃模块不得 import、fetch、link 或以其他方式运行时依赖 `modules-legacy/`。
