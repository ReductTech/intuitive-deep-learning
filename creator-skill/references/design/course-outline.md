## 课程大纲与注册

### 大纲的固定位置

大纲固定为 `modules/<模块目录名>/outlines.json`。执行初始化命令前，必须先读取[工具索引](../tools.md)中的“发现与调用”和“模块大纲与工程创建”，了解调用约定与初始化行为；已读取且仍适用时无需重复加载。随后从仓库根目录执行：

```bash
python creator-skill/scripts/tools.py module.init --directory the_module_name
```

将示例模块名替换为目标模块。脚本在文件存在时直接返回，缺失时创建初始大纲；随后在该文件的 `pages` 中规划和修改页面。

### 工作流程

1. 读取已有大纲和相关材料，了解当前讨论结果与已确认范围。
2. 根据目的、受众和时长，与用户讨论主线、内容取舍和展开顺序；有足够信息时先提出建议稿，再通过讨论逐步完善。
3. 在 `outlines.json` 中维护页面。每页明确主要目标、核心内容和必要的前后衔接，不在大纲中堆积详细布局；讲稿按当前讨论深度逐步补充。
4. 检查目标覆盖、逻辑连续、重复、信息密度和讲述节奏，并根据用户反馈调整。
5. 确认时机与后续制作遵循当前 Workflow。大纲确认后仍可修改，只重新处理受影响部分，不要求整份大纲从头确认。

保留已有页面的稳定 ID。大纲内容已更新、页面已实现和用户已验收是不同状态，不互相代替。

### 大纲与页面变更

用户可以在任何阶段调整内容、页序或页面划分。先判断变化影响哪些页面，再从受影响的阶段继续。

- 仅讨论一种可能方案时，先讨论，不立即改写已确认大纲。
- 用户明确要求调整时，更新原大纲；方向尚未确定时，先说明建议与影响，确认后更新。
- 新增页面按正常的设计、确认、实现和验收流程制作。
- 重排页面时保留原有页 ID，检查前后衔接与实现页序，不因位置变化重做整页。
- 已完成页面仅在受影响时修改；不因后续大纲调整推翻无关的已确认成果。
- 当前页目标或主要内容改变后，原设计确认不再覆盖变更部分，应重新设计并确认。
- 删除、合并或拆分页面时，同步处理受影响的内容、衔接和实现；未同步部分如实说明。

大纲变更后，先处理会阻碍当前制作的影响，再按最新页序继续，不从头重走整套流程。

### 借鉴成熟的大纲结构

设计大纲时，鼓励优先借鉴模型已有知识中熟悉的知名课程、经典教材，以及学术界或行业广泛采用的内容组织惯例。借鉴其主线、先修关系、概念展开顺序和论证方式，再根据本次受众、目标、时长和已有材料调整。

- **仅使用模型已有知识，不联网搜索。** 本环节不为查找、核实或补齐参考大纲而调用搜索、浏览等外部检索工具，也不要求用户另行提供这些知名课程的材料。
- **优先选择熟悉、成熟的结构。** 可以采用某门知名课程或经典教材的组织思路，也可以采用学术汇报、行业报告中广泛使用的叙事惯例；不为显得有出处而寻找冷门案例或堆砌名称。
- **借鉴结构，适配当前任务。** 保留适用的知识依赖和表达逻辑，按实际范围取舍、重排与展开。用户已有明确要求或已确认大纲时，在该范围内借鉴，不擅自推翻原有方向。


### 页面索引

每页使用稳定、简短且有语义的 `id`，例如实际模块中的 `bead-pixels`、`sampling-resolution`。已有 ID 保持不变，不因插入、删除或重排页面重新编号；Guide 与 PPT 使用同一页 ID 对应页面。

以下字段及 JSON 结构保持不变：

- `id`：页面唯一标识，修改已有页面时尽量保持不变。
- `title`：页面标题，优先表达核心结论。
- `goal`：本页需要实现的教学效果。
- `summary`：本页核心内容；必要时说明证据、交互意图和前后衔接。
- `snippet`：本页演讲稿，与页面内容及课程主线一致。

已有模块还可能包含 `interaction`（交互意图）、`next`（下页衔接）、`section`（所属章节）、`references`（参考材料）和 `implementationStatus`（实现状态）。读取原文件后按实际需要维护，不因示例没有列出就删除这些字段；尚未实现的页面不能标记为已实现。

以下展示模块与页面字段的结构；工程入口按实际实现填写：

```json
{
  "id": "example-course",
  "title": "课程标题",
  "description": "课程简介",
  "path": "/modules/example-course",
  "entry": "GuidePage.tsx",
  "ppt": {
    "entry": "ExamplePpt.tsx",
    "path": "/scenedeck/"
  },
  "pages": [
    {
      "id": "intro",
      "title": "页面标题",
      "goal": "当前页所要实现的效果",
      "summary": "本页主要内容",
      "snippet": "本页演讲稿"
    }
  ]
}
```

### 工程约定

- `path` 使用 `/modules/` 加模块目录名的小写形式。
- `entry` 指向模块根目录实际存在的 TSX 文件，组件按文件名命名导出；PPT 入口遵循相同规则。
- `src/app/modules.tsx` 自动发现大纲与模块根目录入口。一般新增课程不需要修改全局路由。
- PPT 入口导出 `deck`；按需导出 `getPptNotes`，通过共享 SceneDeck 播放。
- 大纲阶段允许保存待讨论的结构，但不得将尚不存在的实现标记为已完成模块。
- 正式交付前，核对入口文件存在、已实现页面的 Guide 与 PPT 页序和大纲对应，以及大纲与实际实现相符。大纲可以包含尚待实现的页面，不能因此声称这些页面已经可以播放。
- 页面数量由教学需要决定，不为满足固定数量合并或拆分页面。

### 在原文件中逐步维护

大纲可以先写课程主线，再逐页补充与修改，不要求一次写完几百行。每次以页面 ID 定位本次需要处理的条目，只改相应字段与必要的衔接内容，完成后检查 JSON 格式和页 ID 唯一性。

大纲确认后，在同一个模块目录内补充 React 入口和页面实现。

修改大纲不等于页面实现已经同步。以 `Digital-Image-Intro` 为例，其 PPT 入口按 `outline.pages[n]` 取页面信息，Guide 则显式排列页面组件；插入、删除或重排大纲后，需要检查这些对应关系，不能只改 JSON 就宣称播放顺序已同步。仅修改大纲的任务应说明哪些实现尚待同步，不擅自删除页面代码和资源。
