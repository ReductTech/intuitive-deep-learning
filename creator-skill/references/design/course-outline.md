## 课程大纲与注册

适用于课程、学术报告、技术分享与其他演示的大纲规划和修改。

按“明确任务 → 口头讲顺主线 → 商定章节 → 展开题目与讲稿 → 通读修订”推进。先解决讲述结构，再决定页面数量和表达方式。

### 当前阶段与交付粒度

本规范同时约束聊天回复与文件内容，不以写入 `outlines.json` 为触发条件。先根据当前请求和已有讨论确定交付粒度：

- 用户要求先了解背景、辨析概念、讨论故事或章节时，输出相应分析和粗粒度结构，不提前铺开逐页稿。
- 用户已讨论主线，随后要求“现在设计一个大纲给我看看”“展开大纲”等，默认进入逐页题目与演讲稿；不再次以章节介绍替代大纲，也不要求用户说出字段名才能执行。用户明确只要章节或简版时，以其指定粒度为准。
- 任务刚开始、信息尚不足时，可给暂定主线，并集中询问会实质影响组织方式的条件。缺少受众与时长时，不擅自断言正式页数或内容深度。用户明确要求先给草案时，注明必要假设后交付可调整的草案，不重复访谈。
- 聊天中的逐页草案不等于授权覆盖已有文件。文件更新依用户要求和既有授权执行。

继续对话时，沿用仍然有效的用户主线、概念修正和取舍。不能每次把“大纲”当作从头讨论结构，也不能只把上一轮章节标题换一种说法。

### 1. 明确任务与约束

先读取已有材料和对话，提取已经确定的信息。以下信息用于确定组织方式；缺失且会实质改变方向时集中询问，用户要求先给草案时按上面的暂定假设规则推进。

- **讲者与场合**：谁来讲，在什么场合讲。
- **受众与基础**：主要听众是谁，已经了解什么，关心什么。
- **讲述目的**：希望听众获得什么认识、判断或行动依据。
- **时间安排**：总时长多少，是否包含演示、互动和问答。
- **页面预期**：大约多少页，有无硬性限制，是否允许按内容调整。
- **内容边界**：必讲内容、已有材料、需要复用的成果，以及不希望展开的内容。

可合并询问：

> 这次由谁面向什么听众讲？总时长是否包含互动和问答？预计多少页，还是由我根据时长建议？希望听众听完获得什么，哪些已有内容必须保留？

已知信息不重复询问。用户没有页数偏好时，提出建议范围；不要把页数偏好当作必须补齐的硬性条件。

区分讲者的工作与听众的需求。介绍教师、研究者或团队的实践，不等于要求听众从事同样工作。

仅整理或局部修改已有大纲时，直接沿用已确认约束，不重新启动完整访谈。

### 2. 先口头讲顺整场主线

新建或重构大纲时，先给出一段连贯的口头描述，再列章节。此时不要直接生成几十页目录。

这段描述必须讲清：

1. 听众首先关心什么，为什么愿意继续听。
2. 从这个问题出发，首先需要建立什么认识。
3. 这一认识又引出了什么疑问，为什么需要进入下一部分。
4. 案例、理论、技术和实践分别在何处解决什么问题。
5. 最后形成什么判断，怎样回应开场。

写成能够自然说出来的一段话，不写“第一部分介绍A，第二部分介绍B”的目录复述。

重点检查章节转向。特别是以下变化，必须建立理由：

- 从个人问题转向学科或社会问题。
- 从现象转向理论。
- 从一般讨论转向讲者的项目。
- 从使用者视角转向设计者或实现者视角。
- 从案例展示转向制作方法与技术细节。

如果只能解释两个主题“有关”，却不能解释为什么此刻需要转向，重新调整结构。不要靠“接下来我们介绍……”补过渡。

用户要求先商定粗粒度结构时，在这里停留并讨论。主线已经认可时直接沿用，不重复确认。用户授权一次完成时，自检主线后继续，不额外制造审批步骤。

### 3. 用章节承接问题

依据主线划分章节，不先套用“背景—理论—方法—案例—总结”等固定模板。

每章先明确三件事：

- 它接住了前面留下的什么问题。
- 它让听众获得了什么新的认识。
- 为什么获得这一认识后，还需要继续听下一章。

把这些关系用于解释章节安排，不写入大纲页面字段。

章节可以按知识依赖、问题深化、过程推进或证据展开组织，不强求所有报告采用同一种叙事。

内容相关但不服务于主线时，删减、移动或留作补充。不要因为用户提到某个话题，就给它独立设置一章。

已有材料优先按主线安排，明确保留、重排、合并或删减的理由，不机械保留，也不重复制作相同教程。

### 4. 展开页面前先检验开场与转向

先草拟开场几页和各章节转向处的实际讲稿，再展开完整大纲。

检查：

- 开场是否进入听众的问题，还是先讲了只有讲者关心的背景。
- 举例是否容易理解，是否依赖尚未建立的专业知识。
- 提问是否确实推动当前讨论，还是突然插入了一道测试题。
- 项目出现前，听众是否已经理解它要解决什么问题。
- 技术展开前，听众是否已经知道为什么值得了解实现过程。

默认在工作过程中完成此检验，不额外要求用户逐段审批。用户希望先看部分效果时，再单独展示相应片段。

开场不成立时，先调整进入方式；章节转向不成立时，先调整主线。不要展开整套页面后再用语言润色掩盖问题。

### 5. 逐页撰写题目与演讲稿

每页承担一个主要讲述任务，并对整场推进有作用。内容取舍、前后衔接通过题目、讲稿和页序表达。

#### 题目 `title`

题目应适合直接放在PPT上，让听众知道本页具体讲什么。

- 写清讨论对象和必要范围，不只写抽象概念。
- 可采用明确主题、完整判断或具体问题，按场合选择。
- 不写半句话、空泛口号或故意省略对象的悬念。
- 不为显得正式堆叠名词，也不为追求简短删去必要信息。
- 不把所有标题统一改成对偶、疑问句或“从A到B”。
- 题目必须符合本页实际内容，不能只换词而不检查讲稿。

例如：

- 若实际讨论学生的学习选择，“人工智能时代，大学应该学什么”比“知识的积累与增长”更明确。
- 若实际讨论代码核验，写“AI生成代码的检查与验证”，不写“结果的检查与判断”。

示例只说明题目应当具体，不作为固定命名模板。

#### 演讲稿 `snippet`

写讲者实际准备说的话，不写Summary、内容计划或制作指令。

- 不用“本页介绍……”“讨论……”“说明……”代替实际讲述。
- 按受众基础解释当前内容，提供必要的例子和依据。
- 需要承接时，接住前页已经建立的问题；需要转向时，讲清转向理由。
- 不机械地每页回顾、设问和预告，允许重点展开、短暂过渡和案例演示形成不同节奏。
- 不为吸引注意而虚构讲者经历、受众反应、研究结果或演示效果。
- 区分已实现能力、理论依据、拟议方案与待验证效果。

用户授权生成或重写大纲时，撰写相应讲稿。仅录入或整理材料时，不擅自扩写；缺少的讲稿可以留空。

### 6. 通读整场并修订

完成后，按页序连续阅读讲稿，模拟实际讲述，不只逐页检查。

对每一页回答：

- 听众此刻为什么需要听这一页？
- 前面是否已经建立必要背景？
- 本页增加了什么，而不是重复了什么？
- 讲完以后，下一页为什么需要出现？

不必把答案逐项展示给用户，但必须据此处理结构问题：

- 删去只为覆盖话题而存在的页面。
- 合并没有实质推进的重复内容。
- 补足必要前提，移动出现过早的术语和细节。
- 修复讲述对象、难度或目的突然变化的位置。
- 检查结尾是否回答了开场问题。

根据实际讲稿、推导、演示、互动与停顿估算时长，预留余量。不采用“一页一分钟”等固定换算，不为满足页数机械拆分。

用户反馈“散、跑神、莫名其妙”时，先定位问题层级：受众不符、主线断裂、章节转向、页面内容或措辞。修复对应层级，不立即重写另一套长目录。

用户纠正主线或术语时，先确定其对结构的影响，再修改相应内容。区分用户指定的讲述重点、材料支持的事实和仍需核实的判断；不能把一次强调自动提升为全场中心，也不能只替换术语而保留已被否定的讲述逻辑。若用户的概念解释需要限定，简要说明后给出可用表述，不为表示认同而改写事实。

### 7. 输出与讨论

按当前阶段输出，不一次倾倒所有分析：

- 需求不清：集中询问缺失条件。
- 讨论主线：给出口头描述与粗粒度章节，解释承接关系。
- 展开大纲：按页输出题目和演讲稿；聊天中可用“第 N 页｜题目”及其下方讲稿呈现，无需向用户展示 JSON 字段名。
- 局部修改：只修改受影响部分，并保持前后连贯。

用户已确认的方向直接沿用。用户只讨论一种可能方案时，不立即覆盖原大纲。用户明确要求调整时，在授权范围内修改，不反复索要确认。

输出逐页大纲前，检查交付本身：每页是否有可直接使用的题目，以及讲者能实际说出口的讲稿？“本页讲……”“先介绍……再讨论……”“重点是……”等内容安排不能代替讲稿。若只交付了章节及其说明，应将其称为章节草案，不能声称已经完成逐页大纲。

### 大纲文件与页面字段

大纲固定为 `modules/<模块目录名>/outlines.json`。

执行初始化前，读取[工具索引](../tools.md)中的“发现与调用”和“模块大纲与工程创建”；已读取且仍适用时无需重复加载。随后从仓库根目录执行：

```bash
python creator-skill/scripts/tools.py module.init --directory the_module_name
```

替换为目标模块名。文件存在时脚本直接返回，缺失时创建初始大纲。仅讨论选题或结构时，不必提前初始化。

`pages` 按讲述顺序排列，每页严格只含：

- `title`：本页题目。
- `snippet`：本页演讲稿。

不增加页面 ID、目标、摘要、章节、衔接、交互、来源或制作状态字段。主线、约束、来源、原稿对应和实现映射，按需保存在模块 `_scratchpad/` 或实现代码中。

```json
{
  "id": "example-course",
  "title": "课程标题",
  "description": "课程简介",
  "path": "/modules/example-course",
  "entry": "GuidePage.tsx",
  "ppt": {
    "entry": "ExamplePpt.tsx",
    "path": "/scenedeck/"
  },
  "pages": [
    {
      "title": "页面标题",
      "snippet": "本页演讲稿"
    }
  ]
}
```

### 结构参考与事实依据

可以借鉴模型已有知识中熟悉的课程、教材和报告结构，吸收适用的知识依赖与论证顺序。

不为寻找参考大纲联网检索，不为显得有出处堆砌名称，也不凭记忆声称未经确认的具体结构。用户另行要求研究调研、事实核验或指定来源时，按该任务要求检索。

借鉴结构不替代受众判断，不覆盖用户已确认方向。

### 变更、实现与注册

在原文件中逐步维护，不要求一次写完全部讲稿。用户将提供新版时，等待新版，不提前补全或迁移。

- 新增、删除、合并、拆分或重排后，检查受影响的内容与衔接。
- 局部修改不推翻无关成果，不重新启动整份大纲确认。
- 页面目标或主要内容变化后，按当前 Workflow 重新处理受影响的设计与确认。
- 大纲更新、页面实现与用户验收分别记录，不互相代替。
- 仅修改大纲时，不擅自修改或删除页面代码与素材；未同步实现如实说明。

工程约定：

- `path` 使用 `/modules/` 加模块目录名的小写形式。
- `entry` 指向模块根目录实际存在的 TSX 文件，组件按文件名命名导出；PPT 入口同理。
- `src/app/modules.tsx` 自动发现大纲与模块根目录入口，一般不需要修改全局路由。
- PPT 入口导出 `deck`，按需导出 `getPptNotes`，通过共享术库播放器播放。
- 播放器场景 ID 在实现层维护，不回填到大纲。旧工具依赖旧字段时处理适配，不补回页面字段。
- 大纲可以包含待实现页面，不将不存在的入口或页面宣称为可播放成果。

落盘后检查 JSON 格式、页序和页面字段。交付已实现模块前，再核对入口、Guide 与 PPT 的对应关系。

仅修改 JSON 不代表实际播放顺序已同步。例如 `Digital-Image-Intro` 的 PPT 按 `outline.pages[n]` 取信息，Guide 显式排列组件；重排后必须分别核对。

### 修改本规范后的回归检查

使用以下任务检验实际行为，不只检查规范文字是否完整：

1. **需求缺失**：仅给出一个主题。应先询问受众、时长、页数预期和目的，不直接生成长目录。
2. **跨主题报告**：要求同时覆盖背景、学习建议、项目和技术。应先口头讲清转向理由，再展开章节，不把要求逐项变成并列栏目。
3. **局部反馈**：已有认可主线，用户只说第二页难懂。应检查第二页及邻页，保留无关内容，不重做整场。
4. **讨论转交付**：多轮讨论中用户已纠正开场、主线与术语，随后说“现在设计一个大纲给我看看”。应保留最新修正，输出逐页题目与实际讲稿；不能再交一遍章节说明，不能覆盖未授权修改的文件。
5. **纯聊天与简版**：用户只要讨论故事时不生成逐页稿；后续要求只列章节时仍按章节交付。不能因本规范规定逐页格式而忽略用户指定的粒度。

据实际输出发现的问题继续调整，不以写入了检查条款代替验证。
