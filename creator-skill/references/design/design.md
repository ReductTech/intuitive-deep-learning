# 页面设计指导

页面设计应从教学或表达目标出发，根据受众基础、内容关系和使用场景，决定信息组织、视觉表达与交互方式。本文件适用于教学、科研和商业演示；教学与自学要求仅在对应场景采用。制作顺序、内容确认与修改范围遵循当前 Workflow。

## 1. 先明确页面任务

设计、重设计或评审页面前，先明确：

- **核心问题**：观众看完本页应理解什么、建立什么联系，或能够做出什么判断？
- **受众基础**：观众已经知道什么，哪些概念、条件或推导仍需解释？
- **表达依据**：哪些事实、证据、图形、公式或操作能够支持目标？
- **前后衔接**：本页承接什么，又为后续内容建立什么基础？
- **使用场景**：本页用于引入、讲解、比较、探索、总结还是查阅？

第一页不使用 Shared `ContentBlock`，单独设计封面。其余页面默认使用 `ContentBlock` 的 `title`、`subtitle` 和标准标题区；用户明确要求其他版式时，按指定范围更换。这个要求从设计示意图阶段开始执行，不能等到 React 实现时才补上。

生成设计图前，查看 `modules/shared/react/layout/ContentBlock.tsx` 及其默认样式，依据真实组件确定标题区；不从封面或视觉样例另造标题样式。标题区以下的构图与表达方式由本页任务决定。

每页围绕一个主要问题或理解目标组织内容。多个图形、区域和操作可以共同解释同一问题，不必机械限制元素数量，也不因内容较多就直接拆页。

只保留完成当前目标所需的信息。精简时不得丢失必要条件、对象含义、关键证据和推导关系。数值仅在有助于理解、比较或计算时呈现。

已确认的内容范围、页面划分或设计方向需要实质调整时，遵循 Workflow 确认受影响部分，不擅自扩展任务。

## 2. 先看视觉案例

明确当前页面任务后，在开始设计、重设计或视觉评审前，从 [visual_samples](../../assets/visual_samples/) 中选择相关案例。使用图片读取工具实际打开正例与反例，逐组对照；不能只读文件名、文字说明或缩略图。

`pos_` 表示正例，`neg_` 表示反例。同一主题的两张图必须结合查看。

正例和反例用于比较特定设计决策，不是对某种风格、版式、元素数量或信息密度的普遍评价。

除第一页及用户明确指定的其他版式外，视觉样例只指导 `ContentBlock` 标题区以下的内容，不照搬样例中的特殊标题、页码和分隔线。

分析案例时，关注设计目标、内容组织、视觉表达和交互方式之间的关系，不机械模仿其具体版式。

不因页面简洁就认定其优秀，也不因页面信息较多就认定其不合格。信息密度应与页面任务和使用场景匹配。

反例用于说明特定场景下的设计缺陷，不代表该页面形式在所有场景中都不合适。判断前必须考虑其原本的使用目的。

图片只展示可见状态，不能据此认定交互已经有效、教学效果已经验证或页面已经通过测试。

借鉴案例时提取可迁移的设计方法，不照搬具体构图。没有直接对应的案例时，参考最接近的设计问题，不强行套用无关示例。

页面设计必须服务于当前教学目标，不以视觉风格、元素数量或版式形式直接判断优劣。

### 视觉设计图的工具约束

所有视觉设计图必须使用 **ImageGen** 生成或修改，包括整页设计稿、局部构图、结构图、流程图、科学示意图、重设计预览及多套候选方案。

- 设计图流程绝对不使用 Python，包括 Pillow、Matplotlib、ReportLab 及其他 Python 绘图、排版、渲染或图片后处理脚本。
- 不得改用手写 SVG、Canvas、HTML/CSS 截图、浏览器渲染或其他程序化绘图生成设计图，也不得先用代码绘制主体，再交给 ImageGen 润色以规避要求。
- 需要多套方案时，每套均由 ImageGen 生成；修改、纠错及视觉变体继续使用 ImageGen，不用脚本重绘、拼接或排版成另一张设计图。
- 不因结构简单、科学内容、文字精确、可编辑、矢量交付、效率或工具故障自行设置例外。交付 SVG 或宣称图表可编辑，不能作为绕过 ImageGen 的依据。
- ImageGen 不可用或生成失败时，明确说明情况，保留文案与提示词，不擅自切换为代码绘图，也不将旧图冒充新生成的方案。

此约束针对视觉设计图的创作与修改。设计确认后的 React 页面工程实现，以及用于核验真实实现的页面截图，仍按对应 Workflow 执行；实现截图不得冒充 ImageGen 设计稿或替代所需的设计预览。

### 生图提示词

调用图像生成工具前，根据当前页题目与演讲稿，把设计判断写成具体 prompt，而非只给题目和“美观、简洁、参考样例”等风格词。设计判断留在 prompt 与过程记录，不新增为大纲字段。

- **页面任务**：从当前大纲明确本页要讲清的一个问题，以及必须保留的内容与条件。不自行扩展成另一套主题或学习方法。
- **正反例的取舍**：说明实际查看了哪一组图片、正例中哪种表达值得借鉴、反例中的什么问题需要避免，并落实为本页的构图要求。例如“保持比较条件一致，让差异直接出现在比较对象上”，比“参考正例风格”具体。不要将反例中的所有外观特征一概判为错误。
- **表达与对应**：说明视觉主体是什么，图形中的每个对象、位置、连接或变化分别对应什么内容。没有内容依据时，不添加树、流程、循环或因果箭头。简单文字与对照足以表达时，不强加示意图。
- **组件与样式**：明确第一页封面例外，或使用真实 `ContentBlock` 的标准标题区；正文沿用项目字体与视觉 Token。案例中的特殊标题、字体或配色不自动覆盖工程约束。
- **必要文案与操作**：提供准确的页面文字；确有交互时说明操作对象、变化与解释作用，静态页面不虚构控件。

工具支持参考图片时，可附上所选正例以及必要的真实组件截图，并分别说明参考范围。反例中的问题转写为具体避让要求，不能将反例当作正向样式参考。原始参考图不能代替文字中对当前页内容关系的说明。

保留本次 prompt 与所用样例的路径及取舍说明，和设计图一起放入当前页目录的 `_scratchpad/`；不添加到 `outlines.json`。已查看且仍适用于当前页的案例可以复用，但要重新判断本页如何借鉴。

出图后对照当前页大纲、正反例取舍和组件约束检查结果。若生成图自行添加了关系、换了字体或重做标题区，应修改或重新生成，不能直接交给用户承担这一步检查。


## 3. 让构图表达内容关系

先识别内容之间的关系，再决定主体位置、区域划分和阅读顺序。不先选模板再填内容。

| 内容关系   | 优先考虑的表达                             |
| ---------- | ------------------------------------------ |
| 比较       | 并置对象，保持尺度与条件一致，突出关键差异 |
| 过程       | 按发生顺序展开，保留必要的前后状态         |
| 对应       | 靠近放置，使用稳定的颜色、符号或连接       |
| 层级       | 通过位置、大小和分组呈现主次与包含关系     |
| 因果       | 明确区分条件、变化与结果                   |
| 整体与局部 | 保留整体参照，突出当前观察区域             |
| 数量与比例 | 使用准确的数值、尺度或图形映射             |
| 抽象概念   | 通过具体对象、实例或视觉隐喻建立理解依据   |

这些是构图决策的依据，不是固定版式。选择最能解释当前问题的主体，再安排文字、操作与补充信息。

- 用少量主要区域建立阅读顺序，避免所有内容等权重排列。
- 卡片和边框只用于必要分组，不将每段文字都装进独立容器。
- 标签靠近对应对象，减少跨区域寻找和反复对照。
- 留白用于区分关系、突出主体，不为填满画布增加装饰或重复内容。
- 相关内容共同完成一个判断时保持联系；确实需要不同理解步骤时，再考虑分步展示或调整页划分。
- 不为追求形式简洁而删除必要的上下文、证据或解释。
- 不为追求视觉丰富而添加与当前目标无关的图形、插画和装饰。

## 4. 建立清楚的视觉层级

第一眼应能找到本页主体，随后能理解必要的证据、解释与操作。

通过区域比例、对齐、间距、大小和对比建立主次，避免多个区域同时争夺注意力。次要信息可以弱化，但必须在实际展示尺寸下清楚可读。

- 标题明确提出本页的问题、现象或结论，不使用空泛口号代替信息。
- 主体承载核心关系，辅助信息解释条件、证据或边界。
- 强调色只用于当前需要关注的对象、结论或状态，不让所有内容同时突出。
- 颜色优先表达对象、类别、数值或状态。同一含义保持一致；重要状态还应通过文字、形状或位置提供识别线索。
- 同页相关元素保持必要的视觉联系，避免仅凭颜色或图例才能理解其关系。
- 不以卡片数量、图标数量、颜色数量或装饰复杂度衡量页面质量。

沿用当前项目的字体、基础色彩和 UI。页面可以根据内容采用不同构图，但同一演示中的标题体系、视觉编码和操作习惯应保持稳定。

画布、Typography、组件与样式约束见[工程实现](../engineering/implementation.md)。

尊重已确认的设计方向，不因个人审美擅自重做页面。[个人偏好](../preferences.md)仅在用户要求时采用。

## 5. 保持内容准确、表达一致

使用清楚、自然的书面语言。正文只补充理解所需的信息，不重复图形已经明确表达的内容，也不以空泛口号、无必要的术语或制作说明占据页面。

图形、文字、公式和操作应相互补充。图形无法说明的条件、假设与边界，应明确写出。

- 同一对象在前后页及不同表达形式中保持名称、符号、颜色和含义一致。
- 位置、长度、面积、大小及颜色变化，应准确对应所表达的量或状态。
- 数据、计算、图表和结论相互核对，不为构图方便改变事实或数学关系。
- 公式中的变量、单位、维度与推导关系必须正确；简化表达时不得改变结论成立的条件。
- 真实材料、模拟数据与示意图应清楚区分，不把生成或重绘素材称为历史原图或实测结果。
- 历史、人物和经典实验优先采用真实材料，并核实关键事实；素材难以获得时，可使用准确的重绘或插图。
- 素材必须服务当前表达。来源和背景资料按需要放入讲稿或配套材料，页面保留理解和判断所必需的信息。
- 标题、正文、图形与交互的含义必须一致，不出现标题提出一个问题、主体却回答另一个问题的情况。

## 6. 让交互帮助理解

加入交互前，先明确三个问题：

1. 观众操作什么？
2. 操作后什么发生变化？
3. 这一变化帮助观众理解哪条关系？

只有当操作能够帮助观众观察变化、比较结果、检验预测、理解过程或获得必要反馈时，才引入交互。静态表达已经清楚的内容可以保持静态。

### 操作与结果

- 优先直接操作知识对象；需要控件时，将其放在受影响对象附近。
- 用简短提示和可辨认的状态说明操作方式，不依赖长篇说明。
- 默认状态应呈现观察对象和有意义的初始结果。
- 操作后同步更新相关图形、数值、公式与解释。
- 需要比较时保留基准、前后对照或观察记录，使变化原因容易辨认。
- 操作结果应符合实际机制，不能仅改变颜色、数字或装饰来模拟知识变化。
- 操作自由度应与学习任务匹配。初学者需要明确引导时，不以无限制操作代替教学设计。

### 反馈与恢复

反馈应说明当前发生了什么，以及结果与输入之间的关系。教学任务还应解释判断正确或错误的原因。

根据任务提供重试、重置、撤销或回看。重置后，输入、图形、数值和解释必须恢复一致，不能残留上一次状态。

耗时操作应提供真实的等待、进度和失败反馈，不模拟成功；沿用现有组件和业务接口。

### 动效

动效用于交代对象对应、变化过程和操作反馈。速度应允许观众跟随，关键结果应保留在画面中；较长演示提供暂停、重播或分步控制。

不添加无表达作用的动画，也不让动效遮挡内容或打断阅读。若静态图已经足以说明关系，不必为了增加动感而引入动画。

## 7. 教学场景的学习推进

本节仅适用于教学与自学内容。

先明确学生已有基础，以及学完后应能识别、预测、比较、计算、解释或迁移什么，再选择内容与活动。

- 从可观察的对象、现象或尝试建立理解依据，再引入术语、符号与公式。
- 新内容按照理解依赖展开，必要前提应在使用前建立。
- 一次主要推进一个新关系或判断，避免同时引入大量变量和概念。
- 需要预测时，先给学生形成判断的机会，再展示结果和解释。
- 比较实验尽量保持其他条件稳定，突出当前条件变化的影响。
- 初学时提供必要提示和有限自由度；理解后逐步减少提示、增加探索空间。
- 在后续情境中复用已学关系，通过变式检查学生能否迁移，而非重复相同操作。

开场根据内容选择具体情境、现象、问题或任务，尽快建立学习动机；不强制使用故事，也不机械从定义和目录开始。引入的疑问应在后续得到回应。

每页应形成一次有意义的认知推进。页数服从内容完整性与学习节奏，不机械追求少页或多页。交互不以积分、徽章或操作次数代替理解。

题型与反馈见[习题设计](quiz.md)。

## 8. 自学课程与课程预览

本节仅适用于涉及真实自学课程或课程流程演示的页面。

### 真实自学课程

优先复用 Shared `LessonFlow`，沿用完成条件、进度保存和回看机制。

完成条件应对应实际学习任务。学生能够看出当前需要完成什么，以及完成后如何继续。

### 模拟流程预览

用于展示已有课程的操作与学习流程，不修改原课程的完成条件、播放逻辑或学习进度。

- 演示状态与自动播放逻辑放在展示模块内。
- 模拟操作与画面中的真实入口对应，呈现操作、反馈、解锁和滚动之间的关系。
- 滚动由前一步完成或继续动作触发，不用纯定时滚屏冒充交互流程。
- 支持暂停和重播；离开视窗或切到后台时停止推进，并照顾减少动态效果的偏好。
- 明确标注为流程演示，不将截图上的模拟操作描述为真实课程交互。

### 缩略视窗中的真实体验

直接嵌入原课程，保留原生操作、手动滚动、完成条件和进度保存。不叠加另一套完成按钮，也不以自动播放替代原生流程。

## 9. 实现后检查

依据真实渲染结果检查页面，不能只看设计图或代码。

### 内容与视觉

- 页面是否准确回答当前核心问题？
- 主体、证据、解释和操作的层级是否清楚？
- 阅读顺序是否自然，必要的内容关系是否完整？
- 文字、公式、图表和数据是否准确一致？
- 在实际展示尺寸下，文字与关键标记是否清晰可读？
- 是否存在重复信息、无效装饰或不必要的视觉竞争？
- 是否遵循已确认的设计方向与项目规范？

### 交互与状态

- 默认状态是否有意义，操作入口是否清楚？
- 操作是否产生预期变化，相关图形、数值和解释是否同步？
- 反馈、错误处理、重试和重置是否符合实际行为？
- 动效是否帮助理解，是否存在遮挡、卡顿或无法恢复的状态？
- 是否存在只在截图中看似可用、实际无法操作的控件？

交互行为必须通过实际操作验证，截图不能代替行为检查。

页面制作与修改后执行[基础检查与验收](../eval/checks.md)。仅在用户明确要求时执行 Rubric 评分。
