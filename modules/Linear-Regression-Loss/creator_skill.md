# 课程创作 Skill

## 目标

把老师提供的主题、笔记、截图、教材页面或一段描述，发展成高质量的 React 课程模块。理想结果是一套内容拥有两种自然形态：适合课堂投影的 1600×900 Web PPT，以及适合课后探索的 Blog/Guide 导览页面。

## 核心判断

请把 `modules/Neuron-Guide` 当作设计研究对象，而不是模板。学习它如何把抽象知识变成可观察、可操作、可讨论的过程，学习它对节奏、叙事、状态变化、反馈和信息密度的判断；不要复制它的页面结构、色彩、卡片样式、章节顺序或交互形式。

每门课都应有自己的“视觉隐喻”和界面性格。数学课可以像实验台、地图或推演纸；历史课可以像档案、时间轴或展览；编程课可以像调试现场或机器内部。形式由知识本身决定。设计相似的是认真、克制、可解释和有教学目的，而不是外观相似。

从 Neuron-Guide 借鉴的不是“应该使用某个组件”，而是这些问题：

- 学习者此刻正在观察什么？
- 他做出的动作改变了什么理解？
- 页面为什么现在出现，而不是更早或更晚？
- 视觉、文字和操作是否共同指向同一个概念？
- 这一页结束后，学习者能否用自己的话说明下一步？

## 从输入到设计

输入可能完整，也可能只有一张截图。先提取其中的事实、主张、情绪、视觉线索和不确定之处。不要急着套用现成课件结构；先寻找这门课最值得被看见的关系、变化、冲突或尺度。

与老师共同形成教学 brief 和大纲。默认规模约 22–28 页，但页数服从内容密度和授课节奏。大纲确认后再分批制作，可以一次一页，也可以一次完成几页相互依赖的页面。每页只需说明它在整条认知旅程中的作用、学习者会注意到什么，以及它如何通向下一步；不要求预先规定统一的布局或组件。

课程设计的首要目标是提升认知速度：让学习者更快看见关系、更快形成预测、更快发现矛盾并更快用自己的话复述结论。交互、动画、装饰和版式都只是手段，不是完成度指标。克制是高级：能用一句话、一张图或一个对比讲清楚时，不额外增加控件和视觉噪音。

## 复用与扩展

优先研究并复用 `modules/shared/react/` 中已有的排版、布局、反馈、输入、提问、渐进展示和图表能力。复用的是可访问性、状态处理和交互质量，不是强迫所有课程拥有相同的外观。

### UI Kit 是硬约束

新模块必须大幅复用 `modules/shared/react/` 的 UI Kit，而不是只借用颜色变量。凡是 UI Kit 已经提供的能力，必须直接使用对应组件：

- 普通按钮、链接按钮使用 `Button`；滑杆使用 `RangeControl`；下拉选择使用 `Select`；说明触发器使用 `ExplainPanelButton`。
- 页面标题、正文、标签、公式说明使用 `Typography`；阶段容器使用 `LessonStage` / `ContentBlock`；反馈使用 `Callout` / `NoticeStrip`；数值指标使用 `ValueTile`。
- 禁止在模块中用原生 `<button>`、`<input type="range">` 或一套自定义按钮 CSS 重复实现已有能力。只有图表图例、画布工具、棋盘格选择等确实不是 UI Kit 能表达的专用控件，才允许使用原生交互；必须在代码旁说明原因，并继续复用 Shared Typography、焦点样式和 token。
- 模块 CSS 不得重新定义 UI Kit 的字体、字号、字重、行高或基础按钮外观。需要变化时通过组件 `variant`、`className` 和现有 token 组合表达。
- 交付前逐项检查：所有可点击元素是否能追溯到 UI Kit 组件；所有普通文本是否由 `Typography` 渲染；所有表单控件是否具备标签、键盘操作和禁用态。

复用比例应当是可见的设计事实：一页课件中，主要操作、反馈、标题与内容容器优先来自 UI Kit；只有知识本身需要的图表、公式和专用可视化放在模块目录中。

### 内容密度与素材

内容要足够丰富，不能只用几句结论和一个交互撑满一页。默认课程规模约 22–28 页，并在大纲中安排真实背景、关键概念、对比例子、常见误解、练习/预测、阶段总结和延伸阅读；每页仍只保留一个主问题。

在确实能帮助理解时，可以联网查找或下载图片、历史档案、示意图和其他媒体。下载的素材必须：

- 保存到对应模块目录内，不从 `modules-legacy/` 或运行时远程地址加载；
- 记录来源、作者、许可或访问日期，优先使用公共领域、开放许可或项目自有素材；
- 只有当图片承担叙事、证据或空间定位作用时才加入，避免装饰性堆图；
- 如果没有合适的外部素材，可以使用 SVG、CSS 或 AI 生成插图，并在模块 README/注释中说明其用途与来源。

### 交互比例与页面节奏

- 不是每一页都需要交互。带交互的页面默认不超过整套课程的 50%；其余页面可以是观察、解释、历史证据、公式推导、对比、案例、总结或过渡页。
- 只有当交互能让学习者获得新证据、做出预测、比较两个假设、暴露误解或亲手完成一次推理时，才加入交互。不能为了“看起来丰富”而给每页加滑杆、按钮、弹窗或动画。
- 不要求所有页面使用一模一样的排版。布局应随认知任务变化：历史材料可以像档案，数据关系可以用图表，公式推导可以保留连续阅读，练习页才使用控件。保持 Shared UI Kit 的语义和可访问性，不等于复制同一套卡片网格。
- 无交互页仍然要有明确的阅读节奏和下一步提示：使用 UI Kit 的流程控制“模式 2：下拉提示”（`LessonFlow` 的 `revealMode: 'cue'` / `ScrollCue`，或 `ProgressiveReveal mode="cue"`）提示下一页已经出现，引导学习者向下继续。不要为无交互页虚构一个无意义的“完成”按钮。
- 有交互页可以使用 `cue`、`scroll` 或 `immediate`，由教学节奏决定；模式 2 只承担“下一段已准备好”的轻量提示，不替代真正的内容或反馈。

只有当某种表达方式确实属于本课程，或暂时无法合理抽象时，才放入模块目录。发现跨课程稳定存在的模式，再把它提升到 shared。模块专属资源放在模块内部；不要从 `modules-legacy/` 引入运行时代码或资源。legacy 可以帮助了解项目曾经尝试过的方向，但不把它当作设计范本。

## Web PPT 的本质

项目里的 Web PPT 和 Blog/Guide 属于同一个可组合的 Web 课件系统。现阶段两者按页面一一对应：每个 PPT 页面对应导览中的一个课程单元，使用同一组模块、交互状态和教学叙事。PPT 是课堂投影时的观看方式，Guide 是浏览和滚动时的观看方式；不要把 PPT 当作静态幻灯片，也不要把 Guide 当作另一套内容。

设计时应保留未来的自适应接口，让同一课程单元将来可以根据容器、屏幕和学习情境调整布局、信息密度与节奏，而不必重写教学内容。无论课堂 PPT 还是 Blog/Guide 导览，基础设计画布都统一按 1600×900 制作；不同容器只负责缩放、排列和导航，不改变课程单元的核心构图。

PPT 推荐使用 1600×900 画布，并确保内容自然收进画布；Guide 使用合适的文档流。共享状态时使用模块 Provider，处理好 hydrate、本地状态、错误、加载和回访体验。

## 设计质量

追求有辨识度但不喧宾夺主的界面。让颜色、形状、动效、媒体和控件服务于课程的中心隐喻；避免为了“像课程”而堆卡片、按钮或动画。每一次操作都应该带来新的证据、比较、预测或解释机会。交互可以是选择、拖动、输入、排序、模拟、标注、观察或完全没有交互，取决于它是否真正帮助理解。

允许课程拥有不同的密度、节奏和构图。保持清晰的阅读顺序和足够留白，同时尊重课程自己的视觉语法。所有正文字体、标题、说明文字和标签必须使用 Shared UI Kit 的 `Typography` 组件统一管理，禁止在模块 CSS 或局部 style 中自行指定字体、字号、字重或行高。只有图表、Canvas、公式等非普通文本内容可按其渲染需要设置专属样式。Grid/Flex 子项可收缩，媒体、公式、SVG、Canvas 和交互控件不得撑破布局。

## 协作与交付

先和老师讨论目标学习者、授课时间、已有材料、希望保留的表达和不能改变的事实，再提出大纲。实现时按小批次交付，让老师能针对具体页面调整叙事和视觉方向。不要在没有确认核心方向前一次性生成整套页面。

交付前验证路由、构建、PPT 画布 containment、长文本和不同窗口尺寸；实际操作关键流程，检查初始、变化、完成、重置和回访状态。最后说明哪些内容来自材料、哪些是设计推断、哪些仍需老师确认。

## 判断标准

如果一个页面换到另一门课仍然完全成立，它可能只是通用模板；如果页面的形式只能由这门课的概念解释，它才更接近真正的课程设计。保持 Neuron-Guide 的思考深度和完成度，同时让每门课拥有自己的声音。
